# BusinessToGo App Review — Requirements

## Goal
Recover a trustworthy understanding of this two-year-old SwiftUI app, document its actual behavior and architecture, and establish unit tests, driver-based XCUITest end-to-end tests, and a small risk-focused integration suite before undertaking larger changes. This document plans the work; it does not constitute a completed audit or authorize a rewrite.

## Requirements
- **R1** — Establish a reproducible build and test baseline: record Xcode/Swift versions, simulator destination, package revisions, signing requirements, build commands, and existing test results. Record blockers explicitly rather than treating unexecuted tests as passing.
- **R2** — Produce a source-backed feature inventory covering onboarding, accounts, Kimai, Taiga, time tracking, reports, settings, offline operation, and widgets. Classify each as verified, partial, placeholder, broken, or unverified. Reconcile README claims against observed behavior.
- **R3** — Produce a prioritized review with file/symbol references, evidence, impact, severity, and recommended follow-up. Cover correctness, security/privacy, persistence integrity, sync behavior, concurrency, dependency maintenance, accessibility, and maintainability. Keep confirmed defects separate from hypotheses.
- **R4** — Document the current architecture: module responsibilities and dependencies; app startup; Redux state/actions/effects; dependency injection; routing; API boundaries; SQLite ownership; account storage; offline change tracking; ID mapping; and widget boundaries. Include editable diagrams and source references, distinguishing current behavior from proposed changes.
- **R5** — Provide a documentation entry point with developer setup, supported workflows, troubleshooting, data/reset warnings, and testing instructions. Link existing artifacts under `Doc/` and dependency diagrams; retain them in place and label their verification status rather than silently replacing or relocating them.
- **R6** — Establish isolated test infrastructure for unit, integration, and XCUITest E2E suites. Tests must not access production servers, credentials, Keychain entries, or app databases. Support controlled HTTP responses, fresh dependency instances, temporary storage, deterministic time/calendar settings, and cleanup even on failure. Integration tests must exercise real cooperating components rather than substitute the behavior being tested.
- **R7** — Cover account/session flows: account persistence and selection, offline startup, login success/rejection, logout/reset, and switching between accounts/servers. Check isolation of credentials, cached records, and pending changes. Document unresolved expected behavior before asserting a new product rule.
- **R8** — Cover Kimai local CRUD and online/offline synchronization: initial paginated fetch, customer/project/activity/timesheet relationships, offline edits surviving restart, upload ordering and local-to-server ID mapping, delete/visibility behavior, failed/partial sync, retry without duplicates, and retained pending changes. Specify conflict semantics discovered in the app and OfflineSync; do not invent conflict-resolution behavior.
- **R9** — Cover time/report boundaries through integrated data flows: record creation/editing and persisted values reflected in reports, running entries where supported, midnight, week/month/year boundaries, time zones, and daylight-saving changes. Use explicit clocks/calendars and representative fixtures.
- **R10** — Provide a repeatable local verification command and, once repository hosting and runner availability are confirmed, CI execution with test-result artifacts. Separate fast unit tests, focused integration tests, driver-based XCUITest E2E tests, and optional disposable-server compatibility checks. Track coverage by critical scenario, not only line percentage.
- **R11** — Preserve existing behavior during review and documentation. Implement only explicitly agreed build/test-enabling changes in small steps, with regression tests where practical. Record broader upgrades, refactors, and bug fixes as separate follow-up work. Never reset real user data to make tests pass.
- **R12** — Target the latest stable iOS and latest stable Kimai at execution time, not betas or a historical compatibility matrix. Record and pin exact versions for reproducible verification, updating them deliberately. Inventory widget readiness for near-term development without implementing new widget features. Retain Taiga as explicitly partial, with project-management completion deferred to a separate feature plan.
- **R13** — Unit-test Redux reducer transitions and effects using controlled dependencies, each middleware's behavior, and each app-owned service's public behavior with collaborator doubles. Inventory actual middleware/services before assigning tests; do not introduce new middleware solely for testing. Include success, failure, cancellation where supported, request/DTO mapping, and relevant date/report calculations. Test app-specific contracts with external libraries rather than duplicating their internal test suites.
- **R14** — Use XCUITest E2E tests with a test-only domain driver layer: scenario → root driver → feature driver → private shared context → XCUIApplication. Drivers own accessibility selectors, bounded waits, launch configuration, assertions with forwarded failure locations, and cleanup. Scenarios contain domain actions, not selectors or sleeps. Exercise the real app UI, routing, reducers, and services against isolated storage and controlled HTTP; do not launch into a replacement test-only UI or substitute the whole service layer.
- **R15** — Review and document test allocation by risk in `docs/testing/TESTING.md`: most logic belongs in unit tests, critical user journeys in E2E, and only high-value cross-component contracts in integration tests. For every integration scenario, explain the fault missed by isolated units and why UI coverage alone is insufficient. Service tests using real SQLite/Keychain or multiple real collaborators are integration tests regardless of their test target name.
- **R16** — Document the existing Kimai authentication headers, current supported authentication, compatibility impact, and migration recommendations with official sources. Keep a Bearer-token migration and any credential/UI changes as separately approved implementation work; do not make latest-Kimai tests pass by retaining legacy fixtures or ignoring authentication failures.

## Assumptions
- Confirmed scope: resume active development, starting with rediscovery, documentation, and testing. Widget development and Taiga project management are planned next; neither is to be removed or completed within this review.
- Recommended CI, not yet selected: GitHub Actions with a pinned macOS runner image, explicit Xcode selection, an available latest-stable-iOS simulator, dependency caching keyed by resolved revisions, and `.xcresult` artifacts. Use the same commands locally; avoid silently changing tools via `macos-latest`. Reassess if the repository host or runner constraints favor another provider.
- The initial source inspection found a SwiftUI app with app-level `Components`, local Swift packages under `Modules`, `Common`, and `Foundation`, and external Redux, Dependencies, OfflineSync, LoginService, Router, Moya, Chart, and logging dependencies. Build compatibility has not yet been verified.
- Existing tests include ReduxTestStore examples and template tests; their effectiveness and runtime safety remain unverified. `businessToGo.xctestplan` currently lists the app test target, so package-test execution must be checked separately.
- README claims full Taiga integration and automatic offline sync. Source inspection found Taiga account/UI scaffolding and an empty Taiga project input in `IntegrationsView`; this is evidence to investigate, not proof of a complete feature inventory.
- Early review targets include `KimaiService.login`, which currently accepts a constructed URL without validating credentials; mutable shared API server configuration; account/database isolation; ignored errors; and test dependency defaults. These are investigation leads, not a completed security assessment.
- Package platform declarations include iOS 16, while Xcode build settings also contain iOS 17.5 entries. S1 must record current settings separately from the confirmed latest-stable-iOS policy; any deployment-target changes require an agreed implementation step.
- Confirmed auth gap: `KimaiAuthPlugin.prepare` in `Modules/Kimai/Sources/Services/KimaiService.swift` sends `X-AUTH-USER` and `X-AUTH-TOKEN`. [Kimai's removal notice](https://www.kimai.org/en/blog/2026/removing-api-passwords) states API passwords were deprecated on 7 April 2024 and announces removal after Q2 2026, no later than July 2026. [Current API documentation](https://www.kimai.org/documentation/rest-api.html) specifies `Authorization: Bearer <API token>`. Verify the exact latest release's behavior during S2; the notice alone does not establish which installed release has removed support. Document Bearer migration as a priority compatibility follow-up, not an implemented fix.
- No builds, tests, dependency upgrades, or production API calls were performed to create this plan.

## Implementation Plan
### S1 — Recover Build and Test Baseline
Description: Implements R1 and supports R11. Inventory schemes, targets, package pins, SSH/private dependency access, effective platform requirements, and installed tooling. Record the latest stable iOS/Xcode versions and build the app and widget for that simulator and run existing app/package tests safely after checking for live dependencies. Deliver `docs/development/SETUP.md` and `docs/app-review/BASELINE.md` with exact commands, results, and blockers. Verify by repeating setup/build/test commands against an isolated checkout without touching user data; missing prerequisites remain explicit blockers.

### S2 — Inventory Features and Review Risks
Description: Depends on S1 for runtime verification; static inspection may proceed while build blockers remain. Implements R2 and R3. Walk the main user journeys and trace their code, including partial Taiga functionality and widget readiness for future development. Implements R12 and R16 as well: verify the latest stable Kimai version, document the deprecated auth implementation and current Bearer-token contract with official sources, and identify migration blockers without implementing the migration. Inspect credential handling and log redaction, database ownership/reset behavior, API errors/pagination, sync ordering/retries, date handling, global mutable state, and dependency health. Deliver `docs/app-review/FEATURES.md` and `docs/app-review/FINDINGS.md`, including a ranked follow-up backlog. Verify every finding has source evidence or reproducible steps and every feature has an explicit status; label blocked runtime checks unverified.

### S3 — Document Current Architecture
Description: Depends on S2; implements R4. Deliver `docs/architecture/ARCHITECTURE.md` with editable Mermaid dependency/context diagrams and startup, login, local-edit, and sync sequence diagrams. Describe state ownership, component/package boundaries, dependency lifetimes, API contracts, SQLite schema/change tracking, ID remapping, account isolation, and widget data access if implemented. Inspect resolved external package implementations where critical sync behavior lives. Compare with `Doc/AppArchitecture.png`, `Doc/Flow.pdf`, and existing dependency graphs without relocating them. Verify each major diagram/flow against source paths and label unknowns; do not present recommended architecture as the current design.

### S4 — Create Maintainer and User Documentation
Description: Depends on S2 and S3; implements R5. Update README as the navigation entry point and create `docs/usage/WORKFLOWS.md` covering verified account setup, time entry, reports, offline behavior, sync failures, and recovery. Consolidate setup links and explain credentials, storage, backup/reset implications, and known limitations. Clearly label incomplete Taiga/widget functionality. Verify internal links and walk documented instructions on the agreed simulator; flag steps that remain blocked.

### S5 — Design Test Allocation and Isolated Harnesses
Description: Depends on S1 and S3; implements R6, R14, and R15 and enables R7–R9/R13. Deliver an evidence-backed test matrix in `docs/testing/TESTING.md` mapping each reducer, middleware, service, and critical journey to its primary suite and collaborators. Agree a small test design before test/production changes. Prefer unit tests for logic; retain focused integration coverage for service/SQLite persistence across recreation, OfflineSync dependency ordering/ID remapping and interrupted retry, and account/server credential/database isolation. These boundaries can fail despite passing mocked units, while UI tests make their internal state hard to diagnose. Include controlled HTTP → decoding → persistence coverage in those scenarios instead of creating a duplicate broad suite. Add isolated databases, credential namespaces, transport fixtures, clock/calendar controls, and fresh dependencies. Create the XCUITest root/feature drivers with private shared context and stable accessibility identifiers. Verify a real-app UI launch and one cross-boundary persistence scenario, blocked unexpected networking, failure cleanup, and no cross-test shared server state. Account for `AppLauncher`'s existing XCTest detection so E2E launches the real app, not `TestApp`.

### S10 — Unit-Test Reducers, Middleware, and Services
Description: Depends on S5; implements R13 and most isolated logic coverage for R7–R9. Inventory and test every app-owned reducer, each configured middleware (including app-specific monitor wiring), and each service; record external-library responsibilities and justified exclusions. Cover reducer state/effect/delegate transitions, middleware forwarding/order/side effects and cancellation where applicable, service validation/error propagation, auth headers, endpoint/payload/DTO mapping, pagination decisions, CRUD orchestration, and pure time/report calculations. Use controlled collaborator doubles and deterministic async completion, not real storage or a live server. Reducer-owned effects remain reducer tests where no distinct middleware exists. Verify each inventory entry maps to meaningful success/failure tests or an explicit gap, and the unit suite passes independently. Characterize legacy auth separately from the latest-Kimai compatibility requirement; do not silently turn known defects into desired behavior.

### S6 — Test Account and Session Boundaries
Description: Depends on S5 and S10; implements R7. Unit-test account persistence orchestration, login outcomes, selection, logout/reset, and routing delegates. Add driver-based XCUITest journeys for setup/login, offline relaunch, account selection, logout, and user-visible failure/recovery. Keep a focused integration scenario using real isolated credential/storage adapters and two accounts/servers to verify cached data, credentials, and pending-change isolation, including service/store recreation. Verify independent scenarios and no live credentials. Record defects in FINDINGS and agree intended behavior before narrowly scoped fixes.

### S7 — Test Persistence and Offline Sync
Description: Depends on S5, S10, and the account isolation established in S6; implements R8 and R15. Keep CRUD branches, request mapping, pagination decisions, and isolated error handling in unit tests. Add focused integration scenarios using actual OfflineSync/services, temporary SQLite, and controlled HTTP for persisted CRUD across recreation; paginated decoding into storage; customer → project → activity → timesheet ID/relationship remapping; and interruption after partial success followed by retry. Assert final records, pending-change queues, upload order, and no duplicates or lost edits, including deletion. Cover user-visible offline edit → relaunch → reconnect/sync in the E2E driver suite without duplicating every error permutation. Document observed conflict semantics. Optional latest-stable-Kimai compatibility checks must use a disposable, exact-version-pinned server and modern authentication, subject to Q6; never target the personal server. Report the current auth gap as a blocker where applicable.

### S8 — Test Time and Report Workflows
Description: Depends on S5, S10, and S7; implements R9 and R14. Unit-test date conversion, reducer report selection, aggregation/filtering, midnight, calendar differences, week/month/year rollover, DST, and open-ended records where supported. Add driver-based XCUITest E2E journeys for creating/editing a time entry and observing the correct period/project totals, plus timer controls if implemented. Reuse S7 persistence integration coverage; add a dedicated timestamp storage round trip only if serialization/time-zone behavior spans components and is not already verified there. Verify fixed expected totals and timestamps, real UI navigation, and persistence after relaunch without duplicating the full unit-test boundary matrix in UI tests.

### S9 — Automate Verification and Close the Review
Description: Depends on S6–S8 and S10; implements R10 and completes R3/R5/R15. Document one local entry point with separately selectable unit, integration, and XCUITest E2E suites; ensure app/package targets are discovered and retain `.xcresult` artifacts. Recommend GitHub Actions with a pinned macOS image and explicit Xcode/latest-stable-iOS simulator selection; record the exact available runner/toolchain combination before implementation. Hosting/provider adoption remains a recommendation under resolved Q4, not a prerequisite to local automation. Once adopted, run units and focused integration checks on pull requests and driver-based E2E on pull requests initially, splitting slower scheduled compatibility checks as needed based on measured runtime. Finalize `docs/testing/TESTING.md` with scenario ownership, the reason for each integration test, driver conventions, fixture maintenance, and troubleshooting. Verify local suites and CI where configured, with repeated/order-varied runs for shared-state risks. Record unresolved blockers rather than claiming full latest-Kimai compatibility.
