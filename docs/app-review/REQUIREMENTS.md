# BusinessToGo App Review — Requirements

## Goal
Recover a trustworthy understanding of this two-year-old SwiftUI app, document its actual behavior and architecture, and establish repeatable integration tests before undertaking larger changes. This document plans the work; it does not constitute a completed audit or authorize a rewrite.

## Requirements
- **R1** — Establish a reproducible build and test baseline: record Xcode/Swift versions, simulator destination, package revisions, signing requirements, build commands, and existing test results. Record blockers explicitly rather than treating unexecuted tests as passing.
- **R2** — Produce a source-backed feature inventory covering onboarding, accounts, Kimai, Taiga, time tracking, reports, settings, offline operation, and widgets. Classify each as verified, partial, placeholder, broken, or unverified. Reconcile README claims against observed behavior.
- **R3** — Produce a prioritized review with file/symbol references, evidence, impact, severity, and recommended follow-up. Cover correctness, security/privacy, persistence integrity, sync behavior, concurrency, dependency maintenance, accessibility, and maintainability. Keep confirmed defects separate from hypotheses.
- **R4** — Document the current architecture: module responsibilities and dependencies; app startup; Redux state/actions/effects; dependency injection; routing; API boundaries; SQLite ownership; account storage; offline change tracking; ID mapping; and widget boundaries. Include editable diagrams and source references, distinguishing current behavior from proposed changes.
- **R5** — Provide a documentation entry point with developer setup, supported workflows, troubleshooting, data/reset warnings, and testing instructions. Link existing artifacts under `Doc/` and dependency diagrams; retain them in place and label their verification status rather than silently replacing or relocating them.
- **R6** — Establish an isolated integration-test harness that exercises real application reducers, services, serialization, and temporary SQLite persistence together, replacing only external boundaries as necessary. Tests must not access production servers, credentials, Keychain entries, or app databases. Support controlled HTTP responses, fresh dependency instances, deterministic time/calendar settings, and cleanup even on failure.
- **R7** — Cover account/session flows: account persistence and selection, offline startup, login success/rejection, logout/reset, and switching between accounts/servers. Check isolation of credentials, cached records, and pending changes. Document unresolved expected behavior before asserting a new product rule.
- **R8** — Cover Kimai local CRUD and online/offline synchronization: initial paginated fetch, customer/project/activity/timesheet relationships, offline edits surviving restart, upload ordering and local-to-server ID mapping, delete/visibility behavior, failed/partial sync, retry without duplicates, and retained pending changes. Specify conflict semantics discovered in the app and OfflineSync; do not invent conflict-resolution behavior.
- **R9** — Cover time/report boundaries through integrated data flows: record creation/editing and persisted values reflected in reports, running entries where supported, midnight, week/month/year boundaries, time zones, and daylight-saving changes. Use explicit clocks/calendars and representative fixtures.
- **R10** — Provide a repeatable local verification command and, once repository hosting and runner availability are confirmed, CI execution with test-result artifacts. Separate deterministic integration tests from optional live-server compatibility checks and UI smoke tests. Track coverage by critical scenario, not only line percentage.
- **R11** — Preserve existing behavior during review and documentation. Implement only explicitly agreed build/test-enabling changes in small steps, with regression tests where practical. Record broader upgrades, refactors, and bug fixes as separate follow-up work. Never reset real user data to make tests pass.

## Assumptions
- The first objective is safe maintenance and rediscovery, not new features or framework migration.
- The initial source inspection found a SwiftUI app with app-level `Components`, local Swift packages under `Modules`, `Common`, and `Foundation`, and external Redux, Dependencies, OfflineSync, LoginService, Router, Moya, Chart, and logging dependencies. Build compatibility has not yet been verified.
- Existing tests include ReduxTestStore examples and template tests; their effectiveness and runtime safety remain unverified. `businessToGo.xctestplan` currently lists the app test target, so package-test execution must be checked separately.
- README claims full Taiga integration and automatic offline sync. Source inspection found Taiga account/UI scaffolding and an empty Taiga project input in `IntegrationsView`; this is evidence to investigate, not proof of a complete feature inventory.
- Early review targets include `KimaiService.login`, which currently accepts a constructed URL without validating credentials; mutable shared API server configuration; account/database isolation; ignored errors; and test dependency defaults. These are investigation leads, not a completed security assessment.
- Package platform declarations include iOS 16, while Xcode build settings also contain iOS 17.5 entries. Effective app, test, and widget deployment targets must be established in S1.
- No builds, tests, dependency upgrades, or production API calls were performed to create this plan.

## Implementation Plan
### S1 — Recover Build and Test Baseline
Description: Implements R1 and supports R11. Inventory schemes, targets, package pins, SSH/private dependency access, effective platform requirements, and installed tooling. Build the app and widget for an agreed simulator and run existing app/package tests safely after checking for live dependencies. Deliver `docs/development/SETUP.md` and `docs/app-review/BASELINE.md` with exact commands, results, and blockers. Verify by repeating setup/build/test commands against an isolated checkout without touching user data; missing prerequisites remain explicit blockers.

### S2 — Inventory Features and Review Risks
Description: Depends on S1 for runtime verification; static inspection may proceed while build blockers remain. Implements R2 and R3. Walk the main user journeys and trace their code, including Taiga and widget completeness. Inspect credential handling and log redaction, database ownership/reset behavior, API errors/pagination, sync ordering/retries, date handling, global mutable state, and dependency health. Deliver `docs/app-review/FEATURES.md` and `docs/app-review/FINDINGS.md`, including a ranked follow-up backlog. Verify every finding has source evidence or reproducible steps and every feature has an explicit status; label blocked runtime checks unverified.

### S3 — Document Current Architecture
Description: Depends on S2; implements R4. Deliver `docs/architecture/ARCHITECTURE.md` with editable Mermaid dependency/context diagrams and startup, login, local-edit, and sync sequence diagrams. Describe state ownership, component/package boundaries, dependency lifetimes, API contracts, SQLite schema/change tracking, ID remapping, account isolation, and widget data access if implemented. Inspect resolved external package implementations where critical sync behavior lives. Compare with `Doc/AppArchitecture.png`, `Doc/Flow.pdf`, and existing dependency graphs without relocating them. Verify each major diagram/flow against source paths and label unknowns; do not present recommended architecture as the current design.

### S4 — Create Maintainer and User Documentation
Description: Depends on S2 and S3; implements R5. Update README as the navigation entry point and create `docs/usage/WORKFLOWS.md` covering verified account setup, time entry, reports, offline behavior, sync failures, and recovery. Consolidate setup links and explain credentials, storage, backup/reset implications, and known limitations. Clearly label incomplete Taiga/widget functionality. Verify internal links and walk documented instructions on the agreed simulator; flag steps that remain blocked.

### S5 — Establish Isolated Integration Harness
Description: Depends on S1 and S3; implements R6 and enables R7–R9. First agree a small test design covering injection seams, test target ownership, supported runner, and real-vs-substituted boundaries. Add temporary SQLite stores, isolated credential storage/test Keychain namespace where required, controlled HTTP transport, deterministic fixtures/time, and a small workflow driver if useful. Avoid replacing the services under test with mocks. Handle shared server configuration explicitly so tests cannot contaminate each other. Prove the harness with one reducer → service → SQLite round trip plus one controlled HTTP response through decoding/persistence, rerun in isolation and as a suite, and verify cleanup and blocked unexpected network access.

### S6 — Test Account and Session Boundaries
Description: Depends on S5; implements R7. Add deterministic integration scenarios for account save/reload/selection, online and offline startup, invalid credentials/server responses, logout/reset, and switching between two accounts and servers. Exercise app-level orchestration as well as Login services; assert persisted state and credential/database isolation, not only dispatched actions. Verify each scenario starts independently and cannot use live credentials. Record exposed defects in FINDINGS; agree intended behavior before adding a narrowly scoped fix rather than changing assertions to accept unintended behavior.

### S7 — Test Persistence and Offline Sync
Description: Depends on S5 and the account isolation established in S6; implements R8. Add fixture-driven scenarios for customer/project/activity/timesheet CRUD, pagination, relationship mapping, local edits across store recreation, sequential upload dependencies, deletion, HTTP/auth/decoding failures, interruption after partial success, and retry. Exercise actual OfflineSync integration with real temporary SQLite storage. Verify request payloads/order, final records, ID references, pending-change queues, and absence of duplicates after repeated sync. Document observed conflict behavior and unresolved product decisions. Add optional compatibility checks against a disposable, version-pinned Kimai instance only after Q2 is resolved; never target the configured personal server.

### S8 — Test Time and Report Workflows
Description: Depends on S5 and S7; implements R9. Drive saved and edited timesheets through persistence into the report-selection/aggregation path. Cover midnight, locale/calendar differences, week/month/year rollover, DST, and open-ended records if supported. Verify exact totals, selected periods, persisted timestamps, and restart behavior using fixed fixtures. Add a minimal UI smoke journey only after Q3 is resolved; retain business correctness in deterministic integration tests rather than relying on UI assertions alone.

### S9 — Automate Verification and Close the Review
Description: Depends on S6–S8; implements R10 and completes R3/R5. Document one local entry point for the agreed app/package integration suites, ensure test-plan/scheme discovery includes all intended tests, and capture `.xcresult` artifacts. Add a macOS CI workflow once Q4 is resolved, with explicit Xcode/simulator/dependency configuration and no production secrets. Deliver `docs/testing/TESTING.md` with scenario-to-test mappings, boundary definitions, fixture maintenance, optional compatibility checks, and troubleshooting. Verify a clean local run and the configured CI run where available, including repeated/order-varied runs to expose shared state. Reconcile findings and documentation with results; list remaining risks and deferred work without claiming blocked checks passed.

## Open Questions
- **Q1** — Which iOS versions/devices should be supported, and is the widget part of the maintained product?
- **Q2** — Which Kimai server version and authentication method should be supported, and can we use a disposable server for compatibility tests?
- **Q3** — Should this effort include XCUITest smoke tests, or focus first on integration tests below the UI?
- **Q4** — Which repository host and macOS CI runner should execute the tests?
- **Q5** — Should incomplete Taiga functionality be retained and documented as partial, or excluded from the maintained scope?
